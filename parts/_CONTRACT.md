## 1. 検算（作り終えたら、この順で自分で確認する）

| # | 観点 | 具体的な確認 |
|---|---|---|
| ① | **見えるか** | 隣り合う面に**輝度の段差**があるか。白の上に白いカードを置くだけになっていないか。段差が無ければ、面の色・影・罫のどれか1つで必ず差をつける |
| ② | **読めるか** | 装飾がコピーに1mmでもかぶっていないか。写真の上に文字を置くなら、**半透明のベタパネルは敷かない**（写真が濁る）。グラデか、文字を写真の外へ出す |
| ③ | **自然か** | 動きが**図形として意識に上がっていないか**。気配であるべき。派手な軌道・長い尺・跳ね返りは疑う |
| ④ | **品があるか** | `_tokens.css` に無い色を1つも使っていないか。**差し色は1パーツにつき1箇所** |
| ⑤ | **動かしていないか** | 頼まれていない要素を足していないか。既存要素の位置を動かす追加をしていないか |
| ⑥ | **過剰でないか** | 見せ場が2箇所以上になっていないか。**全部強い＝全部弱い** |

**①が最頻の指摘**になるのは構造的理由がある。白ベースのLPは放っておくと全部が同じ明るさに潰れる。
**「輝度に段差をつける」を最初に確認する。**

---

## 2. 触ってはいけない4つ

- **コピー** — 一字一句。ラベルの追加も不可。原稿に無い言葉を成果物に入れない
- **構成・並び順**
- **フォント**
- **要素の増減** — 「良かれと思って」の追加は成果物に入れない。**提案はチャットで**

---

## 3. 各工夫・パーツが持つべき情報

静的な形だけでは足りない。**挙動と使用上限**を必ず持たせる。

```json
{
  "motion":   "スクロールで何がどう動くか。実装が一意に決まる書き方で。
               ×「ふわっと出る」 ○「下から26px、opacity 0→1、0.5s、cubic-bezier(.23,1,.32,1)」",
  "contrast": "この工夫が輝度の段差を作るか、それとも潰すか",
  "maxPerPage": 1,     // 1ページ内で使ってよい回数。見せ場は1〜2箇所
  "readability": "コピーの可読性に与える影響。下げるなら使わない"
}
```

## 4. 作業の順序

1. **参照画像を必ず開いて見る**。見ずに書かない。寸法・比率は現物に合わせる
2. デモで作る。本番に直接入れない（気に入らない時の巻き戻しが高くつく）
3. 書いたら**自分でスクショを撮って見る**。DOMの数値だけで「直った」と判断しない
4. 共通の仕組みを足したら、**既存のUIを一通り触って確認する**（過去に `transform:none` がタブを壊した）
5. 直す前に「これは**素材か、実装か**」を切り分ける。素材由来はCSSで直らない

---

## 5. 実装の決まり

- 色・余白・角丸・文字サイズ・イージングは `_tokens.css` の変数だけ
- `.wrap` `.sec` `.btn` `.h-eyebrow` `.h-lead` `.nb` `.fx` は再定義せず使う
- スクロール表示は `class="fx"` + `data-fx` + `data-d`。JSは書かない
- 日本語の改行制御は `<span class="nb">` と `<wbr>` を併用（nbだけだと画面外へ溢れる）
- **900px以下で必ず畳む。スマホでは写真をCTAより上に置く**
- 黒（#000系）のベタ面は使わない
- クラス名に固有の接頭辞を付け、他パーツと衝突させない
